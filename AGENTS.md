# AGENTS.md

Guidance for AI coding agents (and humans) working in this repo.

## What this is

**Mochi** — a Tamagotchi-style pet that lives in `wp-admin`. An admin can paste an Anthropic API key and their pet says personality-flavored one-liners while evolving through five stages based on happiness and interactions. Built primarily to exercise `@wordpress/build` (the esbuild-based, convention-over-configuration replacement for webpack/Babel in WP plugin development), and to surface honest feedback on the tool in [`docs/WP-BUILD-FEEDBACK.md`](./docs/WP-BUILD-FEEDBACK.md).

The feature is intentionally small; the point is the tooling exploration. If you're an agent picking up this project in a later session, read the docs directory before making decisions — several non-obvious findings about the tool are encoded there and in the memory system.

## Toolchain

- **Node:** 22 (pinned via `.nvmrc` and `package.json` `volta.node`)
- **Package manager:** pnpm 10 (pinned via `packageManager` field; `pnpm-workspace.yaml` declares `packages/*`)
- **Build:** `@wordpress/build` (`wp-build` CLI)
- **Local WordPress:** `@wordpress/env` (Docker-backed)

Do not use `npm` or `yarn` — the lockfile is `pnpm-lock.yaml`.

## Commands

| Command | Purpose |
| --- | --- |
| `pnpm install` | Install deps |
| `pnpm run build` | One-shot production build into `build/` |
| `pnpm dev` | `wp-build --watch` for incremental rebuilds |
| `pnpm start` | Build, then boot WordPress at http://localhost:8888 (admin / password). Plugin is auto-activated via `.wp-env.json`. |
| `pnpm run env:stop` | Stop containers |
| `pnpm run env:destroy` | Remove containers, volumes, networks |
| `pnpm run env:cli -- <args>` | Pass-through to WP-CLI (e.g. `pnpm run env:cli -- mochi feed`) |
| `pnpm test` | Run both test suites (TS via vitest + PHP via a standalone script) |
| `pnpm test:ts` | Vitest only — `packages/state/src/index.test.ts` |
| `pnpm test:php` | PHP state machine parity tests only — `tests/php/state-test.php`, no Composer / PHPUnit / WP test suite |

Docker Desktop must be running before `pnpm start` / `env:*`.

## Architecture contract — read before modifying anything

1. **PHP is authoritative for game state. TS is the canonical spec. They must stay in parity.** `includes/state.php` is the source of truth at runtime. The TS state machine in `packages/state/` exists as (a) the canonical, unit-testable specification that the PHP must track exactly, (b) type exports for the UI, and (c) future-proofing for a script-module-only UI. **Enforcement has two layers**: (i) hand-written mirror tests in `packages/state/src/index.test.ts` and `tests/php/state-test.php` with matching scenarios and expected values; (ii) **shared JSON fixtures** in `tests/fixtures/state-transitions.json` loaded by both test suites, so any drift fails one side immediately on the same data. Any change to game rules (thresholds, clamps, penalties, evolution gates) must update TS first, then PHP, then the fixture file if the rule change touches an existing scenario. Never ship a rule change without running `pnpm test`.
2. **`packages/state/` holds all pure, Node-testable logic — not just state math.** It currently contains the state machine (`index.ts`) AND page-context greetings (`greetings.ts`, exported from `index.ts`). The split criterion is *DOM access*, not semantic category: any function that's pure (no `document`, no `window`, no `fetch`) belongs here because it's trivially unit-testable in a vitest Node environment. UI-adjacent things like quip tables and greeting selection are fine to live here as long as they take their browser inputs as parameters (`pickGreeting(state, bodyClasses)`, not `pickGreeting(state)` reading `document.body`). If you add new pure helpers used by the UI, put them in `packages/state/` with tests next to them rather than inlining in `StagePanel.tsx`.
3. **The API key is write-only over REST.** `GET /mochi/v1/state` returns only `api_key_configured: bool`, never the key itself. The key is read from `wp_options` inside `includes/ai.php` on the server side and never serialized back to the client. Do not "improve" this by echoing the key back, and do not forward it to any script that runs in the browser.
4. **Only `includes/ai.php` makes network calls.** Every other PHP file is hermetic — pure state transitions, REST handlers, CLI glue. If you find yourself adding `wp_remote_*` or `curl_*` outside `ai.php`, stop and reconsider. Centralizing the outbound-network surface makes it trivial to audit what leaves the site.
5. **`generate_speech()` degrades gracefully.** Missing key, network failure, non-200, malformed JSON → all fall back to `State\stub_speech()` and return `source: 'stub'`. Callers must honor both sources. Do not remove the fallback path; it's how we keep the UI responsive when Anthropic is down, the key is wrong, or the user hasn't configured one yet.
6. **State is stored plaintext in `wp_options`.** Fine for this local demo. Documented with a visible warning in the settings UI. Do not repurpose this pattern for production without replacing the storage layer.
7. **`StagePanel` and `InspectorPanel` are pure components with no wrapper logic.** They deliberately live in files that will not move during the routes migration. The classic mount entry (`packages/ui/src/index.tsx`) and the classic PHP glue (`includes/admin.php`) are the only things that would change. See [`docs/MIGRATION-TO-ROUTES.md`](./docs/MIGRATION-TO-ROUTES.md) for the exact delta. Preserve this property when refactoring.

## Conventions and non-obvious gotchas

These contradict the `@wordpress/build` README. Reading `node_modules/@wordpress/build/lib/*.mjs` is the source of truth.

### `packages/` is flat — one level deep

`getAllPackages` in `build.mjs` globs `packages/*/package.json`. Nested scoped folders (`packages/@mochi/state/`) are **silently skipped** — the build reports success but emits no JS. Put package folders directly under `packages/`; scope the package *name* inside `package.json` if desired.

### `wpScript` is a boolean, not `string[]`

JSDoc in `lib/package-utils.mjs` types it as `string[]`. The code (`build.mjs:499`, `:886`) treats it as a boolean toggle. Always write `"wpScript": true`.

### Module IDs ignore `packageJson.name`

The script-module ID in the generated registry is hardcoded as `@{wpPlugin.packageNamespace}/{folderName}`, not `packageJson.name`. You cannot shadow a published package ID like `@wordpress/boot` from a local workspace package — the inner `name` field is ignored at registry-generation time. This is the blocker documented in `docs/WP-BUILD-FEEDBACK.md` Finding 2a.

### A classic script (`wpScript`) cannot depend on a module-only package

If `packages/ui/` is `wpScript: true` and imports from a package that has only `wpScriptModuleExports` (no `wpScript`), the externals plugin externalizes the import as a script module, esbuild falls back to a dynamic-`require` shim, and the bundle crashes in the browser on load. The fix for us is to declare **both** `wpScript: true` and `wpScriptModuleExports` on any local package that classic scripts depend on (see `packages/state/package.json`). This is documented as Finding 2c in the feedback doc.

### Experimental `routes/` is currently Gutenberg-monorepo-only

Trying to use the `routes/` feature in a standalone plugin hits three structural blockers documented in `docs/WP-BUILD-FEEDBACK.md`. We attempted it, ran into all three, pivoted. If you're tempted to try again, read the feedback doc first and save yourself the install time.

### wp-env deprecation warning

`testsEnvironment: false` in `.wp-env.json` silences the "deprecated options" warning and skips booting the tests container. The flag itself is deprecated long-term but works today; the eventual migration is a separate `--config .wp-env.tests.json` file. Not worth doing until we add PHPUnit tests.

## Editing guidelines for agents

- **Do not edit anything in `build/`** — it's regenerated on every `wp-build` run.
- **Do not replace `pnpm` with `npm`/`yarn`** in scripts or docs.
- **Prefer reading `node_modules/@wordpress/build/lib/*.mjs`** over trusting the package README when behavior is ambiguous — the README has drifted from the code.
- When adding a new package, follow the flat layout. Verify the build log shows `✔ Transpiled <name>` and `✔ Bundled <name>` — silence under those phases means your package wasn't discovered.
- When changing game rules, update `packages/state/src/index.ts` AND `includes/state.php` together. The TS is canonical; the PHP is authoritative.
- Do not change `StagePanel` / `InspectorPanel` to take props or to depend on mount context. They must stay renderable by either `createRoot(...).render(createElement(StagePanel))` (classic) or `<StagePanel />` inside a route wrapper.
- If you're about to do a "small refactor" that spans the classic/routes layout boundary, **re-read `docs/MIGRATION-TO-ROUTES.md` first** to make sure you're not making the eventual migration harder.
